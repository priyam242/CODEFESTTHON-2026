2. WHY PAGE RELOAD / F5 WAS SLOW (~3.2 SECONDS DELAY):
------------------------------------------------------
- Problem Diagnosed:
  * In `client/src/components/IntroSplash.tsx`, the variable `hasPlayedInCurrentSpaBoot = false` was an in-memory boolean variable at the module scope.
  * Whenever the user refreshed the browser with F5 on `/dashboard` or `/tenancy/:id`, the SPA completely re-instantiated, resetting `hasPlayedInCurrentSpaBoot` to `false`.
  * This triggered a 2,800ms (2.8 second) blocking intro animation with delayed phase timers, forcing the user to stare at a blank/loading screen before dashboard routes could render.
- Solution Implemented:
  * In `IntroSplash.tsx`, added path detection: if current `window.location.pathname` is not `/` or `/login` (and without `?intro=1`), `IntroSplash` immediately sets phase to `'done'`, skipping the 2.8s delay entirely.
  * In `client/src/api.ts` and `Dashboard.tsx`, introduced Stale-While-Revalidate (SWR) cache in `sessionStorage`. On page refresh, `tenancyApi.getCachedTenancies()` instantly seeds the dashboard state with 0ms delay, and background network revalidation updates the UI silently.

3. WHY PAYMENT POPUP DID NOT AUTO-CLOSE & REQUIRED MANUAL BUTTON CLICK:
----------------------------------------------------------------------
- Problem Diagnosed:
  * Root Cause 1 (Static UPI QR): An offline static UPI QR (`upi://pay?pa=...`) rendered on a desktop screen has no bi-directional channel with bank UPI apps (PhonePe, GPay, Paytm). When a phone scans the QR, the mobile app completes the transaction on the NPCI network, but emits zero webhook to the desktop browser. Hence, the user previously had to manually click "Payment Sent on UPI App" or "Instant Confirm".
  * Root Cause 2 (Razorpay Modal Collision): When opening the official Razorpay Checkout SDK via `razorpayInstance.open()`, the custom RentShield `PaymentModal` backdrop remained mounted behind Razorpay's iframe. This left a lingering popup behind Razorpay and caused event capture conflicts.
- Solution Implemented:
  * Razorpay Instant Dynamic Checkout is the primary flow: dynamically generated Razorpay orders listen to live WebSocket payment events. As soon as the user completes payment on phone/card/UPI, Razorpay's handler immediately executes.
  * In `PaymentModal.tsx`, `onClose()` is called immediately prior to `razorpayInstance.open()`, unmounting the underlying modal so Razorpay displays cleanly with zero duplicate background dialogs.
  * In `handleDirectUpiSubmit`, `onClose()` is executed immediately (<50ms) upon button click, dismissing the modal instantly while payment verification completes asynchronously.

4. WHY STEP SEQUENCING DRIFTED ACROSS THREE VIEWS:
--------------------------------------------------
- Problem Diagnosed:
  * `Dashboard.tsx`, `TenancyDetail.tsx`, and `LandlordVerify.tsx` previously each maintained disconnected, ad-hoc boolean expressions for step completion:
    - Step 2 checked `tenancy.status === 'APPROVED'` in some places, `signerAudit` in others, and missed landlord receiving QR setup.
    - Step 3 vs Step 4 move-out locks were checked via differing combinations of `depositPaid`, `items.length`, and `aiVerdict`.
- Solution Implemented:
  * Created `client/src/utils/escrowSequence.ts`: A single, authoritative, pure functional state machine (`getEscrowState(tenancy)`) returning strict phase numbers (1 to 6), phase labels, and granular role permissions (`canTenantUploadMoveIn`, `canOwnerApproveAndSeal`, `canTenantPayDeposit`, `canTenantUploadMoveOut`, `canTenantSetRefundUpi`, `canOwnerPayRefund`, `canTenantPayExcessDamage`).
  * Integrated across `Dashboard.tsx`, `TenancyDetail.tsx`, and `LandlordVerify.tsx`, ensuring 100% synchronized state transitions across all three interfaces.

1. ESCROW 6-PHASE STATE MACHINE:
--------------------------------
- Phase 1: `NEEDS_MOVE_IN_ITEMS` (Step 01: Move-In Baseline Photo Evidence)
  * Trigger: Tenancy created; `items.length === 0`.
  * Actions: Tenant uploads room baseline photos with SHA-256 byte hashing.
- Phase 2: `NEEDS_OWNER_SEAL_AND_QR` (Step 02: Owner Seal & Receiving QR Verification)
  * Trigger: Items uploaded; owner review pending or awaiting owner deposit receiving UPI/QR.
  * Actions: Owner reviews photo hashes, counter-signs anti-collusion agreement, and sets deposit receiving UPI/QR.
- Phase 3: `NEEDS_GUEST_DEPOSIT_PAYMENT` (Step 03: Escrow Security Deposit Payment)
  * Trigger: Owner approved baseline; `depositPaid === false`.
  * Actions: Tenant pays deposit via Razorpay Dynamic Gateway or scannable Owner UPI QR. Step 04 move-out audit is strictly locked until funded.
- Phase 4: `NEEDS_MOVE_OUT_AUDIT_AND_GUEST_QR` (Step 04: Move-Out Damage Audit & Guest Refund VPA)
  * Trigger: Deposit paid; tenant vacating property.
  * Actions: Tenant uploads exit photos for all items; Gemini 2.5 Flash multimodal audit computes wear-and-tear deductions; Tenant registers receiving refund UPI/QR.
- Phase 5: `NEEDS_FINAL_SETTLEMENT` (Step 05: Final Escrow Settlement & Refund Payout)
  * Trigger: All items audited; counterparty receiving UPI/QR configured; `status !== 'SETTLED'`.
  * Actions: Owner pays net refund (or tenant pays excess damage) via Razorpay or direct UPI scan. Zero-balance contracts offer 1-click instant settlement.
- Phase 6: `SETTLED_ARCHIVED` (Step 06: Settled & Cryptographically Sealed)
  * Trigger: Net balance settled; status is `SETTLED`.
  * Actions: Tenancy cleared from Active Dashboard workspace for both parties; archived into bottom Settled History stack; Society Move-Out Gate Pass & No-Dues NOC available for 1-click PDF download.
