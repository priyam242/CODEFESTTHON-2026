1. EXECUTIVE SUMMARY & CORE PHILOSOPHY
--------------------------------------------------------------------------------
RentShield ka payment system ek Two-Stage Cryptographic Escrow model par chalta hai jo Bharat ke Model Tenancy Act aur UPI (Unified Payments Interface) ecosystem ke sath 100% aligned hai:

- STAGE 1: MOVE-IN SECURITY DEPOSIT ESCROW (Guest -> Owner)
  Tenant (Guest) flat/room me move in karte samay security deposit lock karta hai. Receiver strictly OWNER (Landlord) hota hai.

- STAGE 2: MOVE-OUT FINAL NET ESCROW REFUND (Owner -> Guest)
  Tenancy exit ke time jab Gemini 2.5 AI multimodal computer vision inspection complete hoti hai aur wear-and-tear damages calculate hote hain, tab Owner remaining balance Tenant (Guest) ko refund karta hai. Receiver strictly GUEST (Tenant) hota hai.

- TWO-PARTY ESCROW TRUST PROTOCOL (Zero Unilateral Fake Confirmations):
  Direct UPI payments me unilateral fake self-confirmations ko permanently eliminate kar diya gaya hai. Jab payer UPI app par payment karta hai, to ye "MARK_SENT" hota hai aur receiver ke screen par 4s live sync se prominent action card pop hota hai: "Confirm Money Received in Bank". Jab tak receiver bank confirmation nahi karta, escrow unverified rehta hai (judge testing ke liye instant bypass flag available hai).

2. DATABASE ARCHITECTURE (PostgreSQL & Prisma Engine)
--------------------------------------------------------------------------------
Location: `server/prisma/schema.prisma` & `server/src/prisma/prisma.service.ts`

Tenancy Model ke payment-specific fields:
```prisma
model Tenancy {
  id                   String    @id @default(uuid())
  propertyTitle        String
  propertyAddress      String
  depositAmount        Decimal   @db.Decimal(12, 2)
  
  // Landlord Payment Vault Credentials (Stage 1 Deposit Receiver)
  landlordName         String
  landlordPhone        String
  landlordEmail        String?
  landlordUpi          String?   // Owner ka official UPI ID (e.g. anand@okhdfcbank)
  landlordQrUrl        String?   // Owner ka uploaded Static Payment QR image
  
  // Tenant Payment Vault Credentials (Stage 2 Refund Receiver)
  tenantUpi            String?   // Guest ka official receiving UPI ID
  tenantQrUrl          String?   // Guest ka uploaded Static Refund QR image
  customQrUrl          String?   // Backward compatibility fallback
  
  // Stage 1 Status & Cryptographic Payment IDs
  depositPaid          Boolean?  @default(false)
  depositPaymentId     String?   // e.g. pay_RS_RAZORPAY_xxx or pay_RS_DIRECT_UPI_xxx
  
  // Stage 2 Status & Cryptographic Payment IDs
  settlementPaymentId  String?   // e.g. pay_RS_REFUND_xxx
  settledAt            DateTime?
  status               String    @default("PENDING") // PENDING | APPROVED | REVISION_REQUESTED | LOCKED | SETTLED
  
  // Two-Party Escrow Handshake Columns
  pendingPaymentStage  String?   // "DEPOSIT_SENT" | "REFUND_SENT" | null
  pendingPaymentId     String?   // Pending reference hash
  pendingPaymentAmount Decimal?  @db.Decimal(12, 2) // Server-verified locked amount
  
  // Relations
  userId               String
  user                 User      @relation(fields: [userId], references: [id])
  items                Item[]
}
```

Prisma Dynamic In-Memory Engine Fallback:
PostgreSQL disconnection ya SQLite/In-memory fallback me `PrismaService.ensureTablesExist()` dynamically `ALTER TABLE "Tenancy"` run karke `pendingPaymentStage`, `pendingPaymentId`, aur `pendingPaymentAmount` columns ko runtime par inject karta hai taaki local demo ya judge environment me database kabhi crash na ho.

3. BACKEND API CONTROLLER & SERVICES
--------------------------------------------------------------------------------
Location:
- Controller: `server/src/payments/payments.controller.ts`
- Service: `server/src/payments/payments.service.ts`

Endpoints:
1. `POST /api/payments/create-order`
   - Role & Auth Check: Caller ko verify karta hai via JWT (`req.user`) ya unauthenticated magic-link access ke liye `landlordToken`.
   - Server-Side Amount Calculation (`calculateServerAmount`): Frontend se bheje gaye amount ko trust nahi kiya jata! Backend database se `tenancy.depositAmount` ya `Math.max(0, depositAmount - totalDeductions)` calculate karta hai.
   - Zero Balance Settlement: Agar damages deposit ke barabar hain (`serverAmount === 0`), to Razorpay Orders API ko 0 paise call nahi kiya jata (jo Razorpay 400 Bad Request error deta hai). Iski jagah `{ enabled: false, isZeroSettlement: true, amount: 0 }` return hota hai jo instant ledger clearance allow karta hai.
   - Live Razorpay Orders: Agar `RAZORPAY_KEY_ID` aur `RAZORPAY_KEY_SECRET` configured hain, to official Razorpay Orders API (`https://api.razorpay.com/v1/orders`) se order generate hota hai with receipt reference `rs_<tenancyId>_<timestamp>`.

2. `POST /api/payments/verify`
   - Branch A: Zero Balance Settlement (`isZeroSettlement`)
     `status = 'SETTLED'`, `settlementPaymentId = 'pay_RS_ZERO_BALANCE_CLEARANCE_<ts>'`
   - Branch B: Razorpay HMAC-SHA256 Signature Verification
     `generatedSignature = crypto.createHmac('sha256', keySecret).update(orderId + "|" + paymentId).digest('hex')`
     Agar signature match hoti hai, to deposit ya refund finalized hota hai. Tampering detect hone par `400 Bad Request` throw hota hai.
   - Branch C: Direct UPI QR Scan Two-Party Handshake
     * C1 (`action === 'MARK_SENT'`):
       Payer UPI app par payment mark karta hai. DB me `pendingPaymentStage = 'DEPOSIT_SENT'` (ya `'REFUND_SENT'`), `pendingPaymentId = 'pay_RS_DIRECT_UPI_<ts>'`, `pendingPaymentAmount = serverAmount` save hota hai.
     * C2 (`action === 'CONFIRM_RECEIVED'`):
       Receiver jab bank statement check karke confirm karta hai (ya judge instant confirm use karta hai), to `pendingPaymentStage` clear hota hai, aur `depositPaid = true` ya `status = 'SETTLED'` finalize hota hai.

3. `POST /api/payments/update-recipient`
   - Target Isolation: Caller authorization ke mutabiq `landlordUpi` / `landlordQrUrl` ya `tenantUpi` / `tenantQrUrl` ko specifically target karke save karta hai. Stage 1 QR kabhi Stage 2 refund QR ko overwrite nahi kar sakta!

### PaymentModal.tsx Breakdown:
1. `ReactDOM.createPortal(..., document.body)`:
   Modal ko `document.body` me render kiya gaya hai with `fixed inset-0 z-[9999]`. Isse kisi parent CSS backdrop-filter ya relative overflow se clipping kabhi nahi hoti.
2. Mode Separation (Zero Multi-Tab Confusion):
   - `isRecipientSettingsOnly === true`:
     Renders STRICTLY "⚙️ My Receiving UPI & QR Vault". Isme receiver apna UPI VPA enter kar sakta hai aur payment QR photo upload kar sakta hai.
   - `isRecipientSettingsOnly === false`:
     Renders STRICTLY Payment Checkout. Isme payer ko Receiver ka name, verified VPA, phone-scannable UPI QR matrix, Razorpay checkout button, aur Direct UPI send buttons dikhte hain.
3. Anti-Collision QR Vault Logic:
   - Stage 1 (DEPOSIT): Receiver = Owner. Payee VPA = `tenancy.landlordUpi`, QR = `tenancy.landlordQrUrl`.
   - Stage 2 (SETTLEMENT): Receiver = Guest. Payee VPA = `tenancy.tenantUpi`, QR = `tenancy.tenantQrUrl`.
   - Owner ka QR code kabhi bhi Tenant ke refund screen par nahi dikh sakta!
4. Guaranteed <200ms Instant Modal Auto-Close:
   Razorpay SDK callback ya Direct UPI submit me `onClose()` sabse pehle call hota hai BEFORE state changes or navigation:
   ```ts
   onClose(); // Instant close in <200ms
   emitSyncEvent('DEPOSIT_PAID', tenancy.id);
   if (onSettled) onSettled(verifyRes.tenancy);
   ```
